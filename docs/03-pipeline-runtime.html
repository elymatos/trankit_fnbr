1. Executive summary

The number of Trankit executions depends on the selected mode. The local command defaults to --predictor lexical, which executes Trankit only once on the raw sentence. It then performs direct FNBr database lookup, Python lexical processing, and deterministic dependency projection—without a second Trankit call. If the command is run with --predictor model, it executes Trankit a second time on the selected, pre-tokenized lexical units. No WebTool process or HTTP service is called in either mode.

The implementation has two type-prediction modes and two dependency sources:

  • Lexical mode: one standard Trankit pass; types come from selected FNBr lemmas; dependencies are projected from the first UD tree.
  • Model mode: the same first pass and lexical processing, followed by a second pre-tokenized Trankit FNBr call for contextual type probabilities.
  • Scaffold source (FNBR_SCAFFOLD_SOURCE or --scaffold-source): projected (default) uses the projected first-pass tree; model uses the second pass's learned dependencies and requires model mode with a jointly trained checkpoint.
Deployed configuration: the Docker service runs model mode with FNBR_SCAFFOLD_SOURCE=model and the joint checkpoint in cache/fnbr-joint. Its head/deprel come from the second pass, and projected_head/projected_deprel keep the first-pass projection. With projected, the second pass's dependency predictions are discarded.

2. Current runtime flow

1

Raw-text Trankit pass

TrankitUDParser.parse(text) invokes the Portuguese Trankit pipeline on raw text. It obtains sentence boundaries, forms, lemmas, UPOS/XPOS, features, UD heads, dependency relations, and character spans. UD contraction expansions are collapsed back to surface contractions for FNBr matching.

↓
2

Direct FNBr lexical lookup

MariaDBLexiconRepository reads forms, lemmas, POS, types, and patterns from the FNBr database using read-only SQLAlchemy access. Database namespace identifiers such as nsp_lemma_event are normalized to the canonical fifteen labels.

↓
3

Python lexical processing

LexicalProcessor builds a lattice containing ordinary lexical candidates, MWE/pattern candidates, and construction matches. It deterministically selects a non-overlapping sequence of lexical units. $... construction abstractions remain evidence in the lattice and do not replace lexical units.

↓
4

Dependency projection

project_dependencies() collapses each selected MWE span into one lexical token, keeps the span's external syntactic attachment, redirects external dependents, renumbers the tree, and validates root, connectivity, and acyclicity.

↓
5

Type evidence

Lexical mode derives candidates from FNBr lemma types. Model mode additionally calls the customized Trankit pipeline with the selected token strings and reads its ranked lemma_type_candidates. With the model scaffold source, the same call also supplies the lexical-unit head and deprel.

↓
6

FNBr-aware response

The response contains the selected sequence, lexical type, ranked type candidates, dependency scaffold (projected or learned, identified by scaffold_source), source token/character spans, complete candidate lattice, and model/schema/lexicon provenance.

Primary implementation: trankit_fnbr/pipeline.py. Runtime assembly: trankit_fnbr/runtime.py.

3. Execution modes

Baseline

Lexical mode

Trankit calls: one raw-text call.

Type source: FNBr database lemma types. If several candidate lemmas have different types, candidates are returned with a uniform prior; ambiguity is not resolved contextually.

Dependencies: projected from the first UD parse.

Needs: Portuguese Trankit model, database URL, and lexicon revision. It does not require a trained FNBr checkpoint.

Deployed

Model mode

Trankit calls: one raw-text Portuguese call plus one pre-tokenized customized call.

Type source: contextual probabilities from the dedicated fifteen-label head.

Dependencies: projected from the first UD parse by default; learned by the second pass when the scaffold source is model.

Needs: everything required by lexical mode plus a trained FNBr checkpoint. The model scaffold source also requires a joint checkpoint whose fnbr.training.json and checksum validate at startup.

GoalRecommended mode
Inspect MWE recognition and lexical typesLexical
Produce the deterministic FNBr lexical projectionLexical
Evaluate contextual type probabilitiesModel
Use the learned lexical-unit dependency treeModel with scaffold source model and the joint checkpoint

4. Original plan versus current implementation

StageOriginal planCurrent implementation
First parserParse raw text to obtain forms, POS, and dependencies.Implemented by the standard Portuguese Trankit pass.
Lexical/MWE serviceSend first-pass output to WebTool for lemma and MWE identification.WebTool is not called. Python code reads the FNBr database directly and owns lexical processing.
Selected unitsBuild a token sequence in which recognized MWEs can be single units.Implemented as a deterministic projection selected from a retained lexical lattice.
Second parserPass selected units as tokens and use its complete parse as the final result.Absent in lexical mode. In model mode, pre-tokenized selected units are sent to customized Trankit; its dependencies are used only with the model scaffold source.
Final dependenciesLearned by the second parser.Projected from the first UD tree by default; learned by the joint checkpoint when the scaffold source is model (the deployed setting).

The current design deliberately separates a lexical type stored in FNBr from a contextual type prediction. A model prediction is evidence and does not overwrite the authoritative lemma record.

5. Trained model and training data

The deployed checkpoint was trained on Portuguese text enriched with FNBr lemma types. Nothing was translated between languages: scripts/convert_dataset.py ran the runtime lexical processor over each Porttinari sentence, collapsed selected MWEs, projected the UD tree onto the selected lexical units, and wrote the selected lemma's type into MISC as FNBRType=<type>. Tokens without a unique typed lemma are marked FNBRStatus=ambiguous or FNBRStatus=unresolved and excluded from type loss.

6. Ways to access the parser

6.1 Local FNBr pipeline — recommended for inspection

conda run -n trankit-fnbr python scripts/analyze.py \
  "ele tomou o café da manhã logo cedo"

This defaults to lexical mode. Standard output is JSON; model-loading diagnostics go to standard error. For compact JSON or piped input:

echo "ele tomou o café da manhã logo cedo" | conda run -n trankit-fnbr \
  python scripts/analyze.py --compact

6.2 Local contextual-model mode

conda run -n trankit-fnbr python scripts/analyze.py \
  --predictor model --top-k 3 \
  "ele tomou o café da manhã logo cedo"

This requires the customized checkpoint configured by FNBR_TRANKIT_LANGUAGE, FNBR_TRANKIT_CACHE_DIR, and FNBR_MODEL_VERSION. To reproduce the deployed configuration, with learned dependencies from the joint checkpoint:

conda run -n trankit-fnbr python scripts/analyze.py \
  --predictor model --scaffold-source model \
  --fnbr-cache-dir ./cache/fnbr-joint \
  --model-version h8418_0-joint-epoch3@202610021100 \
  "ele tomou o café da manhã logo cedo"

6.3 HTTP API

conda run -n trankit-fnbr fastapi run main.py --port 8000

curl -s http://localhost:8000/fnbr/ \
  -H 'Content-Type: application/json' \
  -d '{"text":"ele tomou o café da manhã logo cedo","top_k":3}'
The API mode is selected at process startup through FNBR_PREDICTOR_MODE. Use lexical for the database-derived baseline or model for a trained customized checkpoint. It cannot be switched per request.

6.4 Docker container

Create the deployment configuration first. Set a real read-only database URL and identifiable lexicon revision. For the jointly trained checkpoint, use FNBR_PREDICTOR_MODE=model, FNBR_SCAFFOLD_SOURCE=model, and FNBR_TRANKIT_CACHE_DIR=./cache/fnbr-joint. The mounted cache must contain the Portuguese Trankit model and the customized joint checkpoint with fnbr.training.json (layout in §5). The database URL may use host.docker.internal to reach a database on the Docker host; Compose maps that name to the host gateway, which Docker Engine on Linux does not do by default.

cp .env.example .env
# Edit .env before continuing.

docker compose up --build -d
docker compose logs -f trankit-fnbr

The Compose service publishes container port 80 as 127.0.0.1:8405 (configurable via FNBR_HTTP_BIND/FNBR_HTTP_PORT) and mounts ./cache at /code/cache. It uses the project Conda environment and a single CPU worker. Model loading takes about 20 seconds after the first start; on the first start, missing Portuguese Trankit and XLM-R files are downloaded into the mounted cache. In another terminal:

curl -s http://localhost:8405/health/ready
conda run -n trankit-fnbr python scripts/smoke_http.py

Readiness checks the loaded model and database connection; liveness is /health/live. Do not bind to an external address without TLS and authentication at a trusted reverse proxy.

curl -s http://localhost:8405/fnbr/ \
  -H 'Content-Type: application/json' \
  -d '{"text":"ele tomou o café da manhã logo cedo","top_k":3}'

Stop and remove the service without deleting the model cache:

docker compose down

6.5 Python API — complete pipeline

from trankit_fnbr.runtime import build_pipeline

pipeline = build_pipeline(predictor_mode="lexical")
result = pipeline.analyze("ele tomou o café da manhã logo cedo", top_k=3)

Use predictor_mode="model" only when the customized FNBr checkpoint is configured.

6.6 Standard Trankit only — raw text

from trankit import Pipeline

parser = Pipeline(
    lang="portuguese",
    cache_dir="./cache/trankit",
    gpu=False,
    embedding="xlm-roberta-large",
)
standard_ud = parser("ele tomou o café da manhã logo cedo")

This bypasses FNBr lookup, MWE lattice construction, lexical types, provenance, and dependency projection.

6.7 Customized Trankit only — pre-tokenized input

from trankit import Pipeline

fnbr_parser = Pipeline(
    lang="customized",
    cache_dir="./cache/fnbr-joint",
    gpu=False,
    embedding="xlm-roberta-large",
)
result = fnbr_parser.posdep(
    ["ele", "tomou", "o", "café da manhã", "logo", "cedo"],
    is_sent=True,
)
This is a low-level diagnostic interface. It bypasses database revision checks, candidate provenance, lattice selection, source spans, and projection validation. Callers must not treat it as equivalent to AnalysisPipeline.analyze().

7. Response interpretation

FieldMeaning
selected_lemma_idThe chosen FNBr lemma, or null when unresolved or ambiguous.
lexical_typeThe authoritative type stored on the selected FNBr lemma. It is not a contextual model prediction.
lemma_candidatesAll retained FNBr lemma identifiers for the selected span.
lemma_type_candidatesRanked type evidence. In lexical mode this is a dictionary-derived prior; in model mode it comes from the customized head.
head, deprelThe dependency scaffold: projected from the first UD parse, or learned by the joint checkpoint when scaffold_source is model.
projected_head, projected_deprelPresent only with the model scaffold source: the projected first-pass attachment, kept for comparison.
scaffold_sourceTop-level: projected or model.
source_token_idsThe first-pass word tokens represented by this lexical unit.
start_char, end_charOffsets into the original text.
latticeSelected and rejected lexical/pattern/construction evidence retained for diagnostics.

8. Current boundaries and pending choices

  • The contextual predictor runs after lexical sequence selection and does not currently feed its probabilities back into lemma or MWE selection.
  • When FNBR_SCAFFOLD_SOURCE=model, the second Trankit pass supplies lexical-unit dependencies and the projected first-pass dependencies remain available as provenance. Only use this option with the jointly trained checkpoint; type-only checkpoints have untrained dependency weights.
  • The HTTP endpoint fixes predictor mode and scaffold source at startup through FNBR_PREDICTOR_MODE and FNBR_SCAFFOLD_SOURCE; they cannot be switched per request.
  • The Python pattern matcher covers the implemented pattern subset. Construction matches are diagnostic lattice evidence rather than selected lexical units.
  • A genuine lexicon revision must replace the example webtool46-YYYYMMDD value in .env.example before output is considered reproducible.
  • The deployed joint checkpoint was selected by Trankit's average development CoNLL-U score, not by FNBr macro-F1, and scores slightly lower on type metrics than the type-only checkpoint (§5).
Decision point: the deterministic projection remains the baseline. The joint model was trained on automatically projected dependencies and provisional lemma-type labels; its attachments are a learned syntactic scaffold, not a semantic dependency grammar. Contextual disambiguation still needs independently reviewed ambiguous occurrences for evaluation.
